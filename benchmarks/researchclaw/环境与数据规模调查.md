## 2. 已有调查报告提取的背景边界

本节只记录 `ResearchClawBench 调查与 OpenEvo 适配报告.md` 的背景结论，不代表本轮开始实现。

### 2.1 建议的 OpenEvo adapter 边界

- 保持 `OpenEvo/src/openevo/` 和根 `pyproject.toml` 不变。
- 后续若获准实现，ResearchClawBench 专属逻辑应放在独立的 `OpenEvo/benchmarks/researchclawbench/` 包或外部 experiment layer。
- 建议复用官方 workspace 构造与 `score_workspace()`，另写 OpenEvo batch orchestration，不把官方 ResearchHarness 专属 batch runtime 强套到 OpenEvo。
- 演化对象仅为 `agent_system`；`text_memory`、`skill_bundle`、`parametric_memory` 保持关闭。

### 2.2 ResearchClawBench 目录与官方运行/评分方式

单个任务结构：

```text
tasks/<TaskID>/
├── task_info.json
├── data/
├── related_work/
└── target_study/
    ├── paper.pdf
    ├── checklist.json
    └── images/
```

官方单任务入口为 `python -m evaluation`，由 Web UI 创建标准 workspace；完成后在 Evaluation 页面触发 Score。官方 batch CLI 目前面向 ResearchHarness。评分器以目标论文、隐藏 checklist 和目标图片为 evaluator 侧证据，对文本和图像项目做多模态 LLM 评分，再计算加权总分。

### 2.3 candidate/evaluator 隔离要求

- candidate 只应看到任务说明、`data/`、`related_work/` 及自己的可写 `code/`、`outputs/`、`report/`。
- candidate 不得看到 `target_study/`、checklist、目标论文、目标图片、judge/scorer 源码、judge 凭据、其他 run 或逐项评分理由。
- candidate 和 evaluator 必须使用不同进程或容器；candidate 结束后才由 evaluator 挂载隐藏材料并评分。
- reflector 不得接收 checklist 内容、关键词、目标论文指标、目标图片、evaluator prompt 或 `_score.json` 的逐项内容。

### 2.4 后续必须冻结的实验条件

- 官方 GitHub 基础 40 题保持冻结，只用于最终测试；社区任务用于 Dev/Validation。
- 最终候选确定后冻结 benchmark、OpenEvo、adapter commit 和 evolved `agent_system`。
- Baseline 与 treatment 共享底模、Codex CLI 版本、reasoning level、工具集合、网络策略、最大步数、时间/token 预算、依赖、任务顺序和 seed；唯一处理变量是 `agent_system`。
- 禁止依据官方 40 题结果继续修改系统；Pass@5 仅用于冻结后的最终候选。

### 7.7 重复文件和空间复用

采用“先按文件大小分组，再只对同大小候选做 SHA-256”的只读方法；共对 7,528 个候选文件、119,119,767 bytes（113.60 MiB）做哈希。

- 精确重复内容组：374 组。
- 涉及文件：796 个，其中冗余副本 422 个。
- 理论最大逻辑节省：1,896,637 bytes（1.81 MiB，0.002 GiB），只占 `tasks/` 约 0.12%。
- 现有共享 inode/hard link：0 组。
- 最大单组可节省约 0.82 MiB；其余大多是小型元数据或 Math 任务中的重复小 `.npy`。

结论：直接对基础 clone 做硬链接改造收益极低，还会破坏不可变源数据的简单审计边界，不建议。真正的节省点是避免每个 run 完整复制 1.162 GiB candidate 输入：后续应优先考虑只读 bind mount、受控 reflink/COW 或项目内按 revision 的只读共享缓存，同时保持 candidate 完全看不到 evaluator 目录。

## 8. 后续磁盘预算

以下仅为规划估算，不是正式实验授权：

| 场景 | 输入副本的可计算下限 | 建议预留 |
|---|---:|---:|
| adapter、测试、设计文档 | 通常低于 100 MiB | 1 GiB |
| 项目专属轻量 Python 环境 | 依赖版本未知 | 0.5–2 GiB |
| 下载当前 17 个社区任务 | 1,022.21 MiB payload；若下载缓存与 checkout 并存可接近 2 GiB | 3 GiB |
| 官方 40 任务单次全量 workspace 输入 | 1,189.93 MiB（1.162 GiB） | 加 outputs 后建议 10–20 GiB |
| Baseline + treatment 各 1 次 | 2,379.86 MiB（2.324 GiB）输入 | 建议至少 50 GiB |
| Baseline + treatment 各 Pass@5 | 11,899.30 MiB（11.620 GiB）输入 | 建议至少 100 GiB |

建议在进入 adapter/canary 阶段前至少保留 20 GiB；进入 40 题 paired final 前保留 50 GiB；若计划 paired Pass@5，则保留 100 GiB。最终复核时 934.137 GiB 的可用空间远高于这些保守建议。任务自身可能生成模型、图表或中间数组，且未来任务依赖可能包含重量级科学包，上述预算不包含 CUDA、PyTorch wheel 缓存、容器镜像或外部模型权重。

## 9. 推荐的 clone、缓存和 workspace 管理

1. 将当前两个 clone 视为本项目专属且按 commit 固定的 source trees；不要引用、硬链接或改动任何 ChemBench/OpenEvo 其他 checkout。
2. OpenEvo 体积小，继续使用本项目内独立普通 clone，不使用共享 `.git` object directory，避免跨项目耦合。
3. ResearchClawBench 当前 shallow clone 已足够做 HEAD 级 adapter 研究；只有确需历史时才在明确授权后 unshallow，不另建重复 full clone。
4. 社区任务使用固定 Hugging Face revision 按 task 选择性下载；缓存位置应显式设在本项目内，例如项目专属 `cache/huggingface/<revision>/`，不要写全局 `~/.cache` 或修改全局 Hugging Face 配置。
5. 保留一份不可变 benchmark source。candidate workspace 只提供 `data/`、`related_work/` 和任务说明；`target_study/` 留在 evaluator 专属路径。
6. 若底层文件系统支持，优先使用受控 reflink/COW；否则使用只读 bind mount。不要直接把整个 `tasks/` 挂入 candidate，也不要靠 `cwd` 隔离隐藏答案。
7. 每个 run 使用项目专属、包含 benchmark commit、adapter commit、split、seed 和 run ID 的目录；不复用失败 run，不覆盖既有证据。
8. 输出、下载缓存和 workspace 分开计量。定期只读生成 manifest 和大小报表；任何清理都需单独授权，本轮不清理任何文件。
